# mqvpn cc / スケジューラ検証 (reinjection=off + 2 パッチ, 50ms)

> 更新: 2026-08-22
> 対象ビルド: mqvpn v0.16.0 + scan + rate-limit, reinjection=off (両端)。
> ラボ (MQVPN-NixOS test/) 計測。クライアント (ルーター) 側設定は接続全体へ反映
> (下りにも効く = クライアント主導のネゴシエーションのため)。

## 計測 (50ms RTT, 2500M 要求, 15s)

| クライアント設定 | 上り (受信/ロス/rtrCPU) | 下り (受信/ロス/srvCPU) |
|---|---|---|
| wlb + bbr (現行) | 2,208 / 11% / 63 | 2,467 / 1.3% / 70 |
| wlb + bbr2 | 2,403 / 3.6% / 84 | 2,463 / 1.5% / 92 |
| wlb + cubic | 1,758 / 29% / 85 | 2,481 / 0.76% / 72 |
| minrtt + bbr | 2,438 / 2.1% / 61 | 2,467 / 1.3% / 71 |
| minrtt + bbr (hetero: 15-75ms 混在) | 1000M は正常 / **2500M: 98% ロス崩壊** | — |

## 推論

1. **minrtt は均一遅延ラボでのみ有利に見える** (上りロス 11% → 2.1%、CPU も低い)。
   パス間に遅延差がある hetero 条件では最安 RTT パス 1 本に全トラフィックが集中し、
   単パス容量で崩壊する (2500M で 98% ロス)。**実環境 (7 パス・遅延差あり) は採用不可**。
2. cubic は下り上限最良 (2,481 / 0.76%) だが上り 2500M で崩れる (1,758 / 29%)。
3. bbr2 はロス特性が良いが CPU を消費 (下り 2500M: 92 vs bbr 70)。2 vCPU 実機では余裕が減る。
4. **結論: wlb + bbr が総合的に最良のバランスで現行設定を維持。**

## 補足

- 1000M 要求では全構成 974-990 Mbps / ≤2.3% で差は小さい (差は高レート帯に現れる)。
- 上り 500M: 485-496 Mbps / 0.4-2.6% (CPU 差のみ)。
