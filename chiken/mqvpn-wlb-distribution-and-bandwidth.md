>   - third_party/xquic/src/transport/scheduler/xqc_scheduler_wlb.c
>   - src/flow_sched.c (po_flow_hash 割り当て)
> 先行調査: chiken/mqvpn-wlb-production-collapse.md (崩壊＝単一パス固着) の「逆」
> ＝「いつ複数パスに分散されるか」と、多量セッション時の実効帯域拡大策。

## 0. フロー分類の正体 (flow_sched.c)

`flow_hash_pkt()` の出力で以降の振る舞いが決まる:

| 内側パケット | ハッシュ | 結果 |
|---|---|---|
| TCP (proto 6) | 5-tuple FNV1a | **PINNED** (フロー単位で 1 パスに固定, 60s idle) |
| UDP (proto 17), `udp_pin=false` (既定 wlb) | `MQVPN_FLOW_HASH_UNPINNED` (0xFFFFFFFF) | **UNPINNED → パケット単位 WRR** |
| ICMP / その他 | UNPINNED | 同上 |
| IPv4 `len < ihl+4` / IPv6 `len < 44` / ext-header で直 TCP/UDP でない | UNPINNED または 0 | 同上 (TCP でも截断ヘッダなら漏れる) |
| IPv4 非先頭フラグメント | IP/ID で PIN (別ハッシュ) | PINNED (但しポート非考慮) |

→ **内側 UDP/ICMP は構造的に決してピンされず、常に全パスへ WRR 分散される。**
崩壊 doc は「実トラフィックが TCP なので(UDP は)崩壊対象外」と書いたが、これは
逆: UDP こそ「崩壊しない (=常に分散する)」唯一のトラフィッククラス。

## 1. 逆の条件：いつ複数パスへ分散されるか (既存調査未踏)

### (1) 内側 UDP/ICMP — 常に分散 (最強の逆条件)
`get_path` で `pin_flow = (hash != UNPINNED)` が false → `wlb_wrr_select` のみ
(フロー表へ挿入しない)。各 UDP データグラムは `deficit` 最大の送信可能パスへ独立に
配送。すなわち TCP が 100/x で固着していても、トンネル内 UDP ペイロード
(DNS, DoT/DoH, QUIC, ゲーム UDP, RTP/Zoom/WebRTC, 内包 WireGuard/OpenVPN-UDP,
NTP, SNMP…) は **3 Starlink の和 ~1.3 Gbps を常にaggregatie**。
- 但し WRR の重み `weight ∝ cwnd ∝ BDP` ゆえ、分割は最高 BDP(≒最高 RTT) パスに
  寄る (均等ではない。例 37/35/28 程度)。UDP は順序不要なので再構成崩れは許容。
- 単一 UDP 5-tuple フロー内でパケットが別 RTT のパスへ散る → 到着ジッター。
  QUIC(内トンネル) 等はこのジッターを被る。

### (2) 截断/拡張ヘッダ TCP — 漏れて分散
`flow_sched.c:82-84,107-109` で短い/ext-header パケットは UNPINNED → パケット単位 WRR。
頻度は低いが、IPv6 ext-header (AH/ESP/ルーティング) を通す TCP は順序保持を失って分散。

### (3) ソフトピン溢れ — 「負荷駆動」の分散 (崩壊 doc の"溢れ"の真体)
`get_path` L966-972: ピン済フローのパスが cwnd 封鎖なら、その 1 パケットだけ
`pin_flow=false` にして別送信可能パスへ WRR 配送、**再ピンせず**。
→ **勝者パスの cwnd が飽和すると他パスへ溢れる。** これが崩壊 doc の
「4並列時のみ f2/f3 に一瞬溢れ(≒5%)」の正体。即ち
**セッション数↑ → 勝者 cwnd 飽和↑ → 溢れ↑ → 多パス利用率↑**。
分散は「重み」ではなく「負荷」で駆動する。欠点は別 RTT パスへの溢れが TCP 再構成を
崩し、doc のジッター崩壊(135–1444ms) を生む。トレードオフは調整可能
(溢れは勝者が cwnd 封鎖の時のみ発火；cwnd が深いほど溢れ少ない)。

### (4) 損失/PTO 退避 → 再ピン (動的再分散)
- `wlb_flow_expire` L352-356: 損失率 ≥2% のパスのフローを tombstone → 次パケットで WRR 再ピン。
  勝者パスが損失を発症すればそこから流出 (クリーンな Starlink 崩壊では勝者ロス無で不発)。
- PTO 退避 L948-957: ピン済パスが連続 PTO≥3 なら退避+再ピン (ブラックホール/フェイルオーバ)。
- 復旧 grace L924/984: パス復帰後 1s のパケット単位 WRR + 復帰パス優先 → 重いフローが
  復元パスへ回帰 (意図的な再分散)。

### (5) WRR deficit ラウンドロビン → 重み比例分割 (多フロー)
PINNED TCP でも同時に M フローがピンする際、`wlb_pick_pin_path` は最大 deficit パスを選ぶが、
`wlb_wrr_select` は配送ごとに其のパスの deficit を -1。重み比 r:1 なら新ピンの
r/(r+1) が重パス、1/(r+1) が軽パスへ。故に **多数の同時フロー下ではピンは重み比例で
散り、100/0 ではない** — ただし「ウォームアップ競争(a)」か
「単一パス期間ピン留保 (L1036-1044)」で早期フローが lock される場合のみ 100/0 になる。
ラボの 100/x は実は **単一パス期間バグ + 新パス検知遅れ** の産物
(L995-1009 コメント: "sym P=16 aggregation collapse: 17/0 pin split")。
→ 100/0 は定常 WRR 性質ではなく「早期ピンの過渡的固着」。

### 逆条件まとめ
分散が起きるのは:
1. 内側 UDP/ICMP (常に)
2. 截断/ext-header TCP (常に、稀)
3. 高負荷で勝者 cwnd 飽和 (ソフトピン溢れ)
4. 勝者劣化 (損失≥2% / PTO≥3) → 退避再ピン
5. 復旧時 grace 再分散
6. 多数同時フロー + 均衡重み → WRR 比例分割
7. ウォームアップ/単一パス lock が無い (同時立ち上げ・cwnd 拮抗)

## 2. 多セッション時の実効帯域を太くする方法

崩壊下の天井は 1 Starlink (~458 Mbps)。これを 3 本の和 (~1.3 G) へ近づける策。

### A. 根因: 重みを ∝ スループット(rate) に (BDP/cwnd ではなく)
`wlb_compute_weight` の返値 N (T=max_rtt/2 で配送期待パケット数) は `N ∝ cwnd ∝ BDP`。
配送*率* = N/T ∝ cwnd/rtt = rate。コードは T で割らず、しかも T を全パス共通の
max_rtt/2 にしているため低 RTT パスほどラウンド数が詰まり重みが歪む。
**正解: 重みを経路の推定スループット (例: `bytes_delivered/srtt` の EWMA や `cwnd/srtt`)
にする。** 帯域同値な Starlink なら重み≈等 → ほぼ均等分割 → 和帯域到達。
崩壊 doc の「重みフロア」はその場当たり補修、rate ベース重みが治療。

### B. 重みフロア (doc 案) — 即効 palliative、併用
`max(weight, max_weight/4)` で冷/低RTT パスに最低 25% 量子を確保 → 一部 TCP ピンが
そちらへ。1 パッチ両端、容易。但し比は恣意的で帯域差へ追従しない。まず入れ、A と併用。

### C. ピン再分散 / 期限短縮
60s idle 期限 + 単一パス期間留保で早期ピンが sticky。安価な修理:
- `force_refresh_paths` (新パス/復旧) 時に既存ピンの一部も再評価する
  (doc のフロアはこれをせず、復旧パスのみ tombstone-all で ever_lost_path ゲート)。
- WLB_FLOW_EXPIRE_US 短縮、または「K ラウンド毎に数%のフローを再ピン」を追加。
  多セッション下では再分散が無いと、ピン時点で凍結した分割から抜け出せない。

### D. UDP 経路の活用
UDP は既に分散するため、順序非依存/ジッター許容トラフィック (QUIC, RTP, ゲーム UDP)
は UDP でトンネル内を通すだけで自然に部分的集約を得る。TCP 主体荷では効かぬが、
混載なら無料で集約分を拾う。順序依存の UDP のみ `wlb_udp_pin` モードを検討 (稀)。

### E. ソフトピン溢れのチューニング (負荷駆動集約の獲得)
高セッション数では溢れが既に帯域を広げる。ジッター崩壊無しで帯域を得るには:
- 溢れ先を「最高 deficit」(現 `wlb_wrr_select`) ではなく「送信可能別パスの中で最低 RTT」
  にする → クロスパス RTT 差最小化 → 再構成崩れ低減。
- 溢れ深さを cap (例: 勝者 cwnd 封鎖が X ms 超でのみ溢れ) → 4並列ジッター崩壊を回避。

### F. より多い並列 QUIC 接続 / フロー
集約はフロー粒度 (内側 5-tuple)。**単一エレファント TCP は 1 パスを超えられない。**
故にバルク転送では並列ストリーム (HTTP/3 多重, 複数 TCP 接続, mowe) でピン数を増やす
→ 分割が細かく → 均等に近づき → 和帯域へ。doc も "8+ streams: overhead 消え +15-23%"。
実践的レバー: トンネル内層で並列接続 / MPTCP 的 fan-out を促す。

### 優先順位
1. **rate ベース重み (A)** — 真の修正、RTT/BDP 歪みを排除。
2. **重みフロア (B)** — 即効 palliative (doc 案済)。
3. **refresh 時ピン再分散 (C)** — 多セッション荷が実際に分割を実現。
4. **溢れ先 = 最低 RTT (E)** — 負荷駆動集約をジッター無しで獲得。
5. **UDP は既に集約 (D)** — ドキュメント化のみ。

## 4. 実測 (本ラボ collapse3: A=30/458 B=42+pareto/400 C=35/450)

up.sh で mogami ラボ起動 → bench.sh collapse3 適用 → クライアント(iperf3)→mnet(192.168.100.1)
経由トンネルで計測。ルーター eth1/3/4 の rx を窓 12–20s で差し引き。

| ケース | eth1(A) | eth3(B) | eth4(C) | TOTAL | クライアント表示 |
|---|---|---|---|---|---|
| **TCP -P1 -R (単一フロー)** | 2 | **402** | 2 | ~406 Mbps | 380 Mbps |
| **UDP -P1 -u -R (単一フロー)** | 409 | 360 | 360 | **1129 Mbps** | 1.07 Gbps (loss 11%) |
| TCP -P20 -R | 206 | 448 | 241 | 895 Mbps | 834 Mbps |
| UDP -P20 -u -R | 815 | 660 | 641 | 2116 Mbps | 2.01 Gbps (loss 54%) |

### 実測が示すこと
1. **単一 TCP フローは 1 パス(B=最高RTT)に固定 → 1 Starlink 上限(～400M)**。
   これが本番 speedtest ~450Mbps 頭打ちの正体 (speedtest = 少フロー → ピンで 1 パス張付)。
   warm 定常では最高 cwnd(≒最高RTT) パスが勝つ (doc シナリオ(b) を実測)。
2. **単一 UDP フローでも 3 パスへ 409/360/360 に分散 → ~1.1G**。
   UNPINNED はパケット単位 WRR ゆえ、1 フローでも集約する。これが最大の「逆条件」。
3. **TCP でも -P20 なら 834M に拡大** (206/448/241)。多セッションは WRR 比例分割で
   実効帯域を太くする (doc の "8+ streams +15-23%")。即ち「多量セッション」自体が
   帯域拡大レバー (本 note §2-F)。
4. doc の「100/x 崩壊」は**コールドスタート/ウォームアップ・ロックの過渡**であり、
   パスが揃って温まった定常では WRR は比例分割する。崩壊の本質は
   「単フロー → 1 パス張付」(単一エレファント TCP は 1 パスを超えられない) にある。

### 帯域拡大の実効的結論
- 単一 TCP フローの天井(1 Starlink) を破るには、フローを複数に割る(MPTCP/並列接続)か
  TCP を UNPINNED 化(順序崩れ許容) しかない → §2-F / §1-(1)。
- UDP 主体トラフィックは構造的に集約済 → 順序非依存トラフィックは UDP で通す (§1-(1),§2-D)。
- 多セッション TCP は現状でも集約するが、均等化には rate ベース重み(§2-A)+フロア(§2-B)+
  再分散(§2-C) で天井を 3 本和へ近づけられる。

## 5. 実装 + 実測 (rate-weight パッチ検証)

`xqc_scheduler_wlb.c` に (A) 重みを `N/T_us` (∝ 配送率, 従来は N∝cwnd/BDP) に変更 +
(B) 重みフロア `max(weight, max/4)` (wlb_start_round) + (C) 周期再ピン (flow_expire で
1/8 ずつ tombstone、≈1/s で全ピン再評価) を実装。`patches/xquic-wlb-rate-weight.patch`
として登録、mqvpn-src.nix の patches に追加、up.sh で再ビルド→ラボ collapse3 で計測。

| ケース | eth1(A) | eth3(B) | eth4(C) | TOTAL | 備考 |
|---|---|---|---|---|---|
| TCP -P1 (単一) | 64/106 | 7 | 106/64 | ~177 Mbps | ピン先が **B(最高RTT)→A/C(最高rate)** に反転 ⇒ rate 重みが効いた証 |
| UDP -P1 (単一) | 928 | 258 | 320 | **1506 Mbps** | 非ピンは常に全パス分散 |
| TCP -P20 | 220 | 381 | 195 | **~880 Mbps** | 3 パス全使用(単一パス458の約2倍)、B がやや優位 |
| UDP -P20 | 603 | 364 | 340 | **1307 Mbps** | **3 本和(1308)に到達** ⇒ 非ピンは完全集約 |

### 検証で分かったこと
1. **rate 重み単体(A) は不十分**: 単一フローのピン先は B→A に反転(重み順が rate 順になった証)
   したが、多フローでも「ウォームアップ時の勝者への固着(60s 粘り)」が残り 1 パス集中。
   → フロア(B)+再分散(C) が必要。これらを加えて初めて UDP が和帯域に到達。
2. **UDP(非ピン)は完全集約(~1.3G)**: パケット単位 WRR が rate 重みに忠实に従い 3 パスを
   帯域上限まで埋める。これが「逆条件(1)」の実証でもある。
3. **TCP ピン集約は和帯域に届かず(~880, 単一パスの~2倍)**: 各フローが 1 パスに固定される
   構造的性質のため。20 ピンが 3 パイプを完全には充填しない(特に B がやや多くピンされる)。
   これは重みモデルの問題ではなく「フロー固定」の特性 (doc の "単一エレファント TCP は
   1 パスを超えられない" と同根)。
4. 単一 TCP フローの実効は依然 1 パス上限(今回は rate 最高の A/C に乗るので ~458 寄り) —
   本番 speedtest 頭打ちの根本解決は「フローを複数に割る(MPTCP/並列)」または TCP 非ピン化。

### 残チューニング
- TCP ピン配分が未だ B(最高BDP) 優位気味。再分散を 1/8→より高率、または
  容量比例ピン割当(重み比例ラウンドロビン)に置き換えれば TCP も和帯域により近づく。
- フロア比 1/4 は 3:1 帯域差へは過剰/過小の可能性 → 帯域比へ追従させる。
