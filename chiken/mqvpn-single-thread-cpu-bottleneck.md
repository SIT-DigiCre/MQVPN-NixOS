# mqvpn サーバー単スレッド CPU 飽和 (600Mbps の壁)

> 更新: 2026-08-22 (最終)
> 対象ビルド: mqvpn v0.16.0 + max-paths + xquic-reinjection-scan + xquic-reinjection-rate-limit,
> RelWithDebInfo / シンボル付き。**採用設定: reinjection=off (両端)**。
> ラボ (MQVPN-NixOS test/) 計測。

## 現象 (実環境)

- サーバー: Ryzen 9 7900 (2 vCPU), 7 パス (Starlink×3 / モバイル×3 / eduroam×1), hybrid 無効
- speedtest (下り) で **~600 Mbps 付近でサーバーの単スレッド CPU が 100%** になり頭打ち。
- hybrid (TCP lane) 有効時は ~300 Mbps に低下 (ACK エミュレーションが送信側コストを上積み)。

## 計測環境・方法

- 3 VM (KVM): ルーター (4vCPU) / サーバー (4vCPU) / 下流クライアント。
  クライアント → トンネル (192.168.0.0/24) → サーバー → internet。
- netem をルーター VM 内の WAN NIC (eth2/4-7) に適用 (片道の送信側遅延、limit 100000)。
- iperf3 UDP 15 秒。CPU は `/proc/<pid>/stat` 1 秒サンプル (jiffies/s, 100=1コア飽和)。
- perf: `perf record -F 99 -e cpu-clock -g` (PMU 不要)。
- ツール: `./test/bench.sh latency|hetero|multistream|profile|clean`。設定変更は nix 編集。

## 変遷 (なぜ改善したか)

| 構成 | 800M 受信/ロス | サーバー CPU | 上限 (50ms 下り) |
|---|---|---|---|
| パッチなし + deadline | 707 / 12% | 103 飽和 | ~780 Mbps |
| scan のみ + deadline | 749 / 6.4% | 103 飽和 | ~1.1 Gbps |
| scan + rate-limit + deadline | 764 / 4.5% | 58 | ~1.7 Gbps |
| **scan + rate-limit + off** | **798 / 0.25%** | **63** | **~2.4-3 Gbps** |

- **600 Mbps の壁 = reinjection=deadline の unacked 走査コスト** (在庫 ∝ RTT×レート)。
- rate-limit (2ms スキャン間引き) が deadline 時の CPU 飽和打破の主役;
  scan は 1 回あたりコスト削減 (膝改善)。rate-limit 単独は scan 前提のため適用不能。
- **reinjection=off は別次元** (スキャン自体が呼ばれない、パッチは不活性)。
  deadline のロス回復 (投機的クロスパス複製) を失い、回復は QUIC 標準の PTO に依る。
- スキャン間隔 (1000 vs 2000u) は膝で有意差なし (≤1.2% ロス帯で同等。上限側のみ
  1000u 有利: 2500M で 1,819 vs 1,524-1,690 Mbps)。デフォルト 2000u を採用。

## ロスの機構

- ロスは「送信要求レート − 実効容量」の超過分。2500M・25% ロス時の分解:

| 箇所 | 割合 |
|---|---|
| サーバー側 tun (qlen 500 ≈ 0.7MB) TX drop | ~62% |
| クライアント側カーネル UDP | ~38% |
| トンネル内 / netem | 0% |

- 送信アプリ (UDP) は輻輳制御なし + tun キューは微小 + mqvpn は単スレッド讀出し →
  **カーネルのキューで溢れる** (NET_XMIT_DROP)。qlen 拡張 (500→10000) は実測で無効。
- 実運用は下流が TCP (自動減速) のため超過は起きにくく、本質的には問題にならない見込み。

## 実運用への指針

1. reinjection=off + 2 パッチで実用上限 ~2.4-3 Gbps (600 Mbps の壁は解消)。
2. ロス回復は PTO ベースになるため、実回線で 1 週間程度の A/B 検証を推奨
   (speedtest と実利用の体感、サーバー/ルーター CPU、ロス率)。
3. さらなる帯域が必要なら server 2 インスタンス化 (2 vCPU 活用)。
