# マルチサーバー + ECMP 構成 (ラボ検証)

> 更新: 2026-08-24
> mqvpn v0.16.0 + 3 パッチ + reinjection=off。nixpkgs 2026-08-22。

## 構成

```
下流クライアント (172.16.0.0/12, kea DHCP: IP/GW/DNS=172.16.0.1)
  ──► ルーター (eth0): ECMP デフォルトルート (nhid グループ, フロー単位ハッシュ)
        ├─ client mqvpn-0: tun mqvpn0, パス {eth1,eth3,eth4,eth5,eth6} ──► サーバーA (10.200.0.1:443,  192.168.0.0/24)
        └─ client mqvpn-1: tun mqvpn1, パス {eth1,eth3,eth4,eth5,eth6} ──► サーバーB (10.200.0.1:4432, 192.168.1.0/24)
  サーバーは同じ VM 上に 2 プロセス (systemd: mqvpn-server / mqvpn-server-b)、
  復号後トラフィックを NAT (eth0) → ホスト (mq-mgmt-br0) → 実ネットワークへ (出口は
  サーバーのみ — クライアント/ルーターはトンネル経由以外に外部経路を持たない)。
```

- 実体: サーバー VM 1 台に 2 プロセス（ports 443/4432）。本番では別マシンに分割する運用を想定。
- 管理ネットワーク (mq-mgmt-br0, 192.168.50.0/24): 全 VM の SSH 管理 + サーバーの出口。
  SLiRP は不使用 (mgmt のデフォルトルートを VM 側に置かない → テスト経路の外への直抜けは構造的に不可能)。
- DNS: クライアントは kea のオプション経由でルーター unbound (172.16.0.1) を参照。
  unbound の forwarder (9.9.9.9 / 1.1.1.1) への再帰クエリも ECMP → トンネル → サーバー出口で実インターネットへ。
- ルーターは `services.mqvpn.clientPorts = [ 443 4432 ]` で 2 クライアント (systemd: mqvpn-0 / mqvpn-1)
  を一様生成。サーバー IP (auth) と WAN NIC (interfaces) は共通、**port のみ**がクライアント間で異なる。
  `manage_routes = false` で mqvpn 側のルーティング操作を止め、`mqvpn-ecmp-assert` 常駐 unit
  が次の 3 つを 3 秒周期で保守する:
  - **サーバーピン**: `<server-ip>/32 via <WAN GW>` (manage_routes=false では上流の
    setup_routes が動かないため自前でピン。WAN デフォルトが消えても制御プレーンが生存する。
    GW は可視の WAN デフォルト優先、無ければ dhcpcd の現在リース (routers=) で補完。
    GW が無い IF はスキップ — on-link の connected ルートに任せる)
  - **ECMP デフォルト**: nexthop オブジェクト (nhid) 方式。トンネル 1 本 = nh 1 個
    (id 1000+i)、生存集合をグループ id 2000 に毎ループ add-or-replace で同期し、
    デフォルトは `nhid 2000` を指す (replace は未存在対象を作らないため add 併用)。
    tun 再作成でカーネルが nh ごと削除しても、グループは自動縮退し**ルートは
    生存メンバーで継続** (黒塗りゼロ)。全滅時はカーネルがグループ・ルートを
    自動削除 → fail-open へ。※ iproute2 は新構文: `group 1000/1001` (重みは
    `1000,1/1001,1`)、空グループは作成不可
  - **fail-open**: 全トンネル死亡時は WAN デフォルトを復元 (遷移時のみ成功ログ、
    失敗は毎ループログ — 古い GW は dhcpcd リースで自己修復)
- NAT: ルーターは mark 方式 (eth0 入力で MARK) → `nixos-nat-post` に全トンネルの
  mark ベース MASQUERADE (externalInterface 未設定のためモジュール総称ルールが併存するが、
  明示のため extraCommands も残す — nixpkgs 更新で挙動が変わり得るため)。
  FORWARD 許可は nat モジュールが生成する `-i eth0 -j ACCEPT` + FORWARD policy ACCEPT
  (旧 `extraForwardRules` は nftables 専用オプションで iptables 実装では no-op だったため削除済み)。
- パスの共有 (同一 NIC 5 本を 2 トンネルで分割利用) のスケジューリング影響は
  `chiken/mqvpn-ecmp-shared-paths.md` にて検証済み (劣化なし)。

## ECMP ハッシュポリシー (重要)

- デフォルト (`fib_multipath_hash_policy=0`) は **L3 ハッシュ (src/dst IP のみ)** のため、
  同一宛先の多数フローは 1 つのトンネルに集中する。
- `net.ipv4.fib_multipath_hash_policy = 1` (**L4: IP+ポート**) にすることで
  フロー単位で均等分散される。configuration.nix に bake 済み。

## 検証結果 (全部 IPv4 で計測 — curl -4)

| テスト | 結果 |
|---|---|
| トンネル確立 | サーバー 2 プロセス / ルーター 2 client / tuns 各 192.168.x.2-1 |
| 単フロー v4 | 200 OK、どちらかの tun を通過 |
| ルーター自身 6 フロー (2 宛先) | 全 200、tunA/tunB 両方に分散 |
| 下流 16 並列 v4 (同一宛先, L3 hash) | **全フロー tunA に集中** (L3 ハッシュのため) |
| 下流 16 並列 v4 (L4 hash 適用後) | **tunA +2,680B / tunB +2,720B ≈ 50:50 分散** |

- クライアント→ルーターの流量は eth1 / tun の /proc/net/dev カウンタで確認。
- 注: クライアントは IPv6 (SLiRP RA) 経由で外部へ抜けるため、計測は `curl -4` 必須。

## ECMP 経由の帯域検証 (LAN クライアント → トンネル)

> per-tunnel 直結テスト (宛先 = tun peer 192.168.x.1) ではなく、**ECMP デフォルト
> 経由**で LAN クライアントから流すテスト。宛先はサーバー側の専用アドレス
> `10.99.0.15` (クライアント/ルーターの例外ルートに無い → 必ず ECMP → トンネル)。
> iperf3 UDP 15s、クライアント rmem 64MB 適用済み。並列はポート別サーバー
> (iperf3 は 1 テスト直列のため)。

| テスト | 各フロー | 合計実効 | ロス |
|---|---|---|---|
| UP 1×2500M (単一フロー→ハッシュで 1 トンネル) | 2,392 | 2,392 | 4.3% |
| UP 2×1250M 並列 | 1,222 + 1,223 | **2,445** | 2.2% |
| UP 2×2500M 並列 | 1,753 + 1,757 | 3,510 | 12% |
| DOWN 2×1250M 並列 | 1,247 + 1,247 | **2,494** | **0.2%** |
| DOWN 2×2500M 並列 | 2,076 + 2,072 | 4,148 | 17% |

所見:
- **実用域は ECMP 経由でも per-tunnel と同等以上**: DOWN 合計 ~2.5G @ 0.2%、UP ~2.45G @ 2.2%。
- 単一フロー 2500M は 1 トンネルにハッシュされ、単一トンネル上限 (~2.4G) と一致。
- 2×2500M での高ロスはラボ特有の RTT≈0 問題 (内部バッファ・ソフトドロップ、
  `chiken/mqvpn-loss-investigation.md` 参照)。実遅延では顕在化しにくい。

テスト用の一時変更 (config 未反映、ラボのみ):
- サーバー VM: `10.99.0.15/32` on lo + iperfd 6207-6209 (-B 10.99.0.15)
  （ECMP 経由で届くサーバー側アドレス。クライアントはこの IP へ iperf を打つ）
- **戻りルートは付けない**。本構成はルーター側 NAPT(MASQUERADE) のため、復路の
  宛先はクライアント実IP(172.16.0.0/12)ではなくトンネル端点(192.168.0.2)になり、
  サーバーの `192.168.0.0/24` connected route だけで足りる。サーバー→クライアント
  実IP を直接叩くテストは NAPT 構成では意味がない（SLiRP 環境でのみ有効なシナリオ）。
  DOWN 計測は mnet(192.168.100.1) 宛にクライアントから `-R` で打ち、実効データを
  トンネル端点宛に戻す NAPT 互換の流れで行う。

## フェイルオーバー挙動 (検証済み)

| 事象 | 挙動 |
|---|---|
| サーバー B 停止 | ハッシュが B に当たったフローだけ失敗 (~2-5 割)。**ECMP 単体は自動フェイルオーバーしない** |
| トンネル B 再作成 (tun 消失) | カーネルが **ECMP ルートごと全削除** → keeper が**生存トンネル (A) のみで ≤3 秒で再アサート** (旧: 全面不達) |
| 全トンネル死亡 | **WAN デフォルト復元 (fail-open)** ≤3 秒 |
| 復旧 (B 復活) | 新規フローから両トンネルへ再分散、12/12 OK |

- 対策: `mqvpn-ecmp-assert` 常駐 unit が**生存トンネルのみ**で再アサートする
  (全滅判定ではない)。tun 消失→ルート全削除後も、生存トンネル 1 本に対して
  `ip route replace default` が最長 3 秒で復元する。全トンネル死亡時は WAN デフォルトに
  フォールバック (fail-open)。
- サーバー制御プレーンは常時 `<server>/32 via WAN GW` でピンされ、
  デフォルトルートの状態と独立に生存する (接続/再接続の前提)。
- 既存フローの振り替えはない (新規フローから正常化)。セッション継続が必要なら
  別レイヤでのハンドオフが要検討。

## 残課題

- 実機 (7 パス) でのパス共有 + マルチクライアント合計帯域のキャリブレーション
  (hetero 条件の数値は `chiken/mqvpn-ecmp-shared-paths.md` 参照: 合計 ~4.4-4.6G)。
- フロー単位 vs コネクション単位の粒度 (現状: フロー単位で OK)。
- サーバー 2 プロセスの帯域共有 (同一 VM: 単スレッド×2 → CPU 2 コア併用)。
- リダイレクト/障害時のフォールバック (トンネル断 → ECMP nexthop 死の挙動)。
- クライアント IP の固定化: mqvpn v0.16 はプール自動割当のみ (固定オプション無し)。
  複数クライアント運用では「NAT 前提・IP 不定」が原則 (FW/ACL はトンネルサブネット単位で書く)。

## テスト環境の設計課題

- 各 VM の管理用 SLiRP NIC がテスト経路に漏れる構造は、**専用 tap ブリッジ
  (mq-mgmt-br0, 192.168.50.0/24) への移行で解決済み**:
  - VM 内の mgmt にデフォルトルートを置かない + ホスト側の転送許可は
    **192.168.50.2 (サーバー) 限定**で、テスト流量がテスト経路 (eth0 → ルーター →
    トンネル) 以外へ抜ける経路が構造的に存在しない (サーバーのみがトンネル集約点
    としてホスト経由で実ネットワークへ出る)。
  - SLiRP が配る 10.0.2.0/24 の衝突 (全 VM が同一 IP) も消滅。
  - SSH は各 VM の mgmt IP (192.168.50.1/2/3) へ直接接続。
- ルーター tun の DOWN (RX) カウンタは正しく計上される (DOWN 400M/8s で +408MB =
  送受信一致)。以前「0 のまま」に見えたのは UP のみの計測だったため。
  DOWN の実効データは NAPT によりトンネル端点(192.168.0.2)宛に戻るため、
  サーバーの `192.168.0.0/24` connected route でトンネルへ乗る。戻りルート
  (172.16.0.0/12 → mqvpn0) は不要（NAPT 構成では意味がない）。
