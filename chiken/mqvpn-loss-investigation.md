# 高レート時のロス: 原因究明 (並列 2 トンネル測定)

> 更新: 2026-08-22。ラボ (2 サーバー/2 クライアント, iperf3 UDP 下り, 20s, RTT≈0)。

## 前提

- 遅延なしラボで並列 2500+2500M の測定をすると 6-21% と暴れる UDP ロス (実行ごとに変動大)。
- netem 50ms ありでは同程度の合計 (2,463M) でロスは 1.4-1.5% に収まる。
- 全て回線容量 (10G virtio×N) を大幅に下回る要求帯域。

## カウンタ観測 (ロスの消失位置の特定)

| 場所 | 観測値 | 判定 |
|---|---|---|
| クライアント (iperf 受信端) | `RcvbufErrors` が **801,914** (rmem 適用前、並列テストの累積)。rmem 64MB 適用後は並列でも**増加ゼロ** | 受信ソケット溢れは事前に存在したが、rmem 後は原因でない |
| サーバー (送信側) | `Udp:SndbufErrors` = 255 (観測窓内で**増加なし**) | 送信ソケット溢れなし |
| ルーター | 全 IF (eth2/7, mqvpn0/1, eth1) の rx/tx_drop 増分 **0** | カーネルでのロスなし |
| ホスト tap | ts-mq / trw0-4 の rx/tx_drop 増分 **0** | tap でのロスなし |

## バイト勘定 (ホスト tap 実測, #8 の窓)

| tap | 方向 | 流量 |
|---|---|---|
| ts-mq (サーバー側) | サーバー送信 | **12.81 GB** |
| trw0 (ルーター eth2) | サーバー→ルーター | 6.19 GB |
| trw4 (ルーター eth7) | サーバー→ルーター | 6.62 GB |
| trw1/2/3 (eth4/5/6) | — | 0 GB (使用していない) |
| **合計 (ルーター受信)** | | **12.81 GB = 送出と一致 (0.0% 差)** |

- 途中 (#7) では trw0/trw2 の 2 本だけを観測し「5.90GB しか届いていない」と誤解したが、
  全 5 ポート観測で解決 (データは trw4 側に着いていた)。
- ロスは**回線/ブリッジ/tap には一切存在しない**。

## 推論

1. **回線・ホスト・カーネルはロスゼロ**。並列時に残る 6-21% は
   **mqvpn/xquic 内部のソフトドロップ** (送信キュー or 受信側再整列バッファの溢れ。
   カーネルカウンタに現れず、実行ごとのバラつきもここから来る)。
2. クライアントの受信ソケット溢れ (rmem 前の ~80 万相当) は高レート測定の
   追加要因であり、rmem 拡大で解消可能 (単一 2500M は 1.4%)。
3. **RTT≈0 で増幅**: 遅延ゼロでは CC のパケット化が平滑化されず内部バッファを
   溢れさせる。netem 50ms あり (2,463M 合計 / 1.4-1.5%) は CC が時間領域で
   動作するため低ロスに保たれる → 実運用 (実遅延) では顕在化しにくい問題。
4. パス数 5→2 で差が出なかったのは、ロスの主因が「パス分散のスケジューラ」ではなく
   「トンネル実体の内部バッファ」であることと整合 (断定はできないが排除の証左)。
